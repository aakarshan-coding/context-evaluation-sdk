# contexteval v1 architecture

## Problem

`contexteval` must explain why a RAG app's context failed without the user rewriting the app. The user hands over one function, `answer(question) -> str`. Everything else (capturing retrieval, swapping chunks for replays and experiments, grading, labeling) happens from the outside, through patched library methods and a context variable. Three things make the shape non-obvious. First, one mechanism has to serve capture, diagnosis replay, and experiments, and it has to work the same way for chromadb, pinecone, and a hand-written retriever. Second, experiments must never see gold data (plan item 15), while replays need it. Third, the acceptance bar is deterministic labels on planted failures with no network, so the demo app and its fake LLM are part of the architecture, not test scaffolding. The 16 resolved items in `plan.md` are fixed constraints. They include verbatim evidence with an 80% token rule, a flaky rerun before replay, the ignored-before-irrelevant ladder, sync-only hooks, in-process one-at-a-time execution, stdlib-only core, and pgvector through the decorator.

## Usage (caller's view)

Quickstart, as the README would show it.

```bash
pip install "contexteval[openai,chroma]"
contexteval init --provider openai          # creates .contexteval/{config.json,contexteval.db}
contexteval build-tests ./docs              # synthetic cases with verbatim evidence; shows cost, asks y/N
contexteval run my_app:answer               # every case through answer(); graded traces stored
contexteval diagnose                        # labels each failure of the latest run
contexteval experiment top_k=3,10 rerank=none,lexical order=as_is,ends
contexteval ui                              # http://127.0.0.1:8765
```

The user's app is unchanged unless it has custom retrieval.

```python
# my_app.py
import chromadb, openai

col = chromadb.PersistentClient("db").get_collection("docs")
llm = openai.OpenAI()

def answer(question: str) -> str:
    hits = col.query(query_texts=[question], n_results=4)       # hooked: n_results is top_k
    context = "\n\n".join(hits["documents"][0])
    r = llm.chat.completions.create(model="gpt-4o-mini",
        messages=[{"role": "user", "content": f"{context}\n\nQ: {question}"}])  # hooked
    return r.choices[0].message.content
```

Custom retrieval names its top_k parameter in the decorator.

```python
import contexteval

@contexteval.retriever(top_k="limit", text="body")   # items are dicts; text lives under "body"
def search(query: str, limit: int = 5) -> list[dict]:
    return pg.execute("SELECT id, body FROM docs ORDER BY emb <-> %s LIMIT %s", (embed(query), limit))
```

Production capture is the same one line at app start. With no CLI run active, each LLM call closes one ungraded trace (the retrievals since the last LLM call plus that call), which `contexteval diagnose --run <production run>` labels with the judge.

```python
contexteval.init()   # returns InstallReport, e.g. {"chromadb": "installed", "pinecone": "not_installed", ...}
```

## Shape

**Module map.** The package has fourteen modules plus `ui.html`. The public surface is `contexteval` (`init`, `retriever`, `InstallReport`) and `contexteval.types`. Everything else is underscore-private (`_capture`, `_hooks`, `_intervention`, `_text`, `_llm`, `_store`, `_runner`, `_diagnose`, `_sweep`, `_testset`, `_cli`, `_ui`), so an app that imports an internal is visibly reaching past the API, per the importable-internals red flag. `contexteval/demo/` (app, fake_llm, planted, corpus) ships in the package so `contexteval run contexteval.demo.app:answer` works after install.

**Data structures first** (per foundational-thinking, type-system-discipline). `types.py` holds the core types.
- `TestCase(id, question, expected_answer, evidence: Evidence | None, source)`. `CaseId` is a content hash, so rebuilding a test set upserts and never duplicates. `Evidence` is proven verbatim only in `_testset.parse_generated`.
- `Trace(question, outcome: Answered | Crashed, retrievals, llm_calls, metrics, test: TestOutcome | None)`. One union makes "answered and crashed" impossible. One optional field covers "graded iff from a test case". `prompt_text` and `in_prompt` are derived properties. The active Setting lives on the trace's run, not the trace, so there is one source for it (the store joins it into `StoredTrace`).
- `RetrievalEvent` keeps both `retrieved` (what the store returned) and `delivered` (what user code got after the intervention). `locate_gold` reads `delivered` and the prompt, and the UI shows both.
- `Diagnosis = Missing(cause, confirmed) | Irrelevant | Ignored | NotContext | Flaky | Judged(verdict, rationale)`. Each variant carries its replay outcomes as evidence. `label_of` and `source_of` are derived with an exhaustive `match`, never stored as a second field.
- `Setting` is the experiment knob record. It has fields only for plan item 15 knobs, so it cannot produce a gold transform. Experiments cannot leak the answer, by construction.

**One intervention mechanism** (per model-the-domain). `Intervention(top_k, transforms)` is the only way context changes. `Transform` is a closed union: knob transforms (`LexicalRerank`, `Reorder`, `KeepFirst`, `Compress`) and gold transforms (`InjectEvidence`, `GoldToTop`, `OnlyGold`), applied by one pure `apply_transform` with an exhaustive match. `Setting.intervention()` compiles knobs in one fixed order. `_diagnose.REPLAY_INTERVENTION` maps each replay step to an Intervention. Both hand it to `_runner.execute`, the single execution path for baseline, replay, and experiment.

**Hooks** (per boundary-discipline). `_capture` owns four context variables: `_active` (the run's mutable `ActiveRun` with question, intervention, and event lists), `_ambient` (production buffer), `_suppressed`, and `_retrieving` (the outermost hooked retrieval in progress, so a hooked store it calls underneath records nothing and the outermost retrieval owns the event and the transforms). It also owns two intercept functions every hook calls. `intercept_retrieval(codec, call, bound_args)` offers the run's top_k to `codec.override_top_k(args, top_k)` (the argument form is implemented once on `RetrievalCodec`; the framework codecs set the retriever's own knob and return a restore that runs after the call), and a hooked call underneath takes the value when the outer layer could not, calls through, decodes to `Chunk`s, applies the intervention (query falls back to the run question for vector-only stores like pinecone), records with the knob that was set, and re-encodes only when the intervention is not a no-op. `intercept_llm` records only. `_hooks` holds all library knowledge as one `HOOKS` table of `HookSpec(library, candidate targets, codec or adapter)`. Patching is class-level. Wrappers carry `__contexteval_original__`, so install is idempotent and `uninstall_all` restores originals for tests. The `@retriever` decorator builds a `_DecoratorCodec` from its arguments and goes through the same `intercept_retrieval`. Chromadb, pinecone, LangChain and LlamaIndex retrievers, and custom code therefore share one code path. The SDK's own provider calls run inside `suppressed()`, so the grader and judge never record themselves. Hook-internal errors fall back to the unmodified call, and user exceptions propagate.

**Modes.** `Mode` is OFF, CLI, or PRODUCTION, owned by `_capture`. The CLI installs CLI mode before importing the user module, so a user `init()` inside `my_app` stays a no-op and `contexteval run` never writes production traces.

**Diagnoser** (per model-the-domain). The logic is data plus one sequencing function. `locate_gold` is pure (IN_PROMPT, DROPPED, NOT_RETRIEVED). `LADDER = ((GOLD_TO_TOP, Ignored), (ONLY_GOLD, Irrelevant))` encodes plan item 5's priority. `MISSING_CAUSE` maps location to cause. `diagnose_case(location, replay)` takes a `Replay = Callable[[ReplayStep], ReplayOutcome]`, so the full table is unit-tested with a scripted replay and no app. It runs the flaky rerun first, then the inject confirmation for missing, then the ladder lazily. Since v1.1 A each step is sampled up to N times (default 3) and a majority decides, so a case costs up to `MAX_STEPS * N` app calls. Cases without evidence and production traces go to `judge`.

**Store** (per make-operations-idempotent). The tables are `test_cases`, `runs`, `traces`, `diagnoses`, and `experiments`. CHECK constraints mirror the type invariants (answer xor error, `passed` null iff no case, experiment runs have an experiment id). A run is an immutable event committed per trace, so a crash leaves a valid partial run. `diagnose` skips already-diagnosed traces unless `--force`, so rerunning after a crash resumes. Experiment tables are derived with `GROUP BY`, never stored.

**Call chain for `contexteval experiment`.** `_cli.cmd_experiment` calls `_runner.run_experiment`, which calls `run_case`, then `execute`, then the user `answer`, then a patched method, then `_capture.intercept_retrieval`. That is three package files a reader traces (`_cli`, `_runner`, `_capture`), plus `_hooks` for the library shape.

**Interface depth.** App code sees two names. `init()` hides library detection, version-drifted targets, idempotent patching, and production buffering. `@retriever` hides result decoding and encoding for three item shapes, top_k override, and intervention. The CLI hides the rest. `Store` exposes domain types only. The SQL and JSON encodings stay private.

**Test strategy.** No test uses the network. An autouse fixture makes non-loopback `connect` raise. The SDK LLM is `FakeProvider`, which dispatches on `LLMRequest.task` and the structured `inputs`, not on prompt text. The app LLM is the real `openai` SDK over `httpx.MockTransport` backed by `demo/fake_llm.respond`, so P1's real-SDK hook path is what the acceptance test exercises. Chromadb runs ephemeral with a deterministic `HashEmbedding`, so no ONNX download happens, and telemetry is off. Pinecone is a stand-in class patched through `_hooks.patch_method` with the real `PineconeCodec`. `demo/planted.py` is the single list of planted cases. The demo cases, the fake LLM script, and the expected labels all derive from it. Each fake rule names the context condition under which the model answers correctly, so the expected label follows from the rule plus the ladder (table in `fake_llm.py`). `FlipFlop` persists a per-question counter because `run` and `diagnose` are separate processes. Test layers: pure units (`_text`, transforms, `diagnose_case` table, `parse_grid`, schema round-trips), hook tests against real chromadb and the openai SDK over mock transport, and two acceptance tests through `_cli.main` for DoD items 2 and 3.

## Synthesis decision

Four runners sketched v1 independently (opus, fable, sonnet, haiku). A fable cross-judge scored them 28, 20, 21, 17 on a six-part rubric and recommended the opus candidate as base. My own read agreed. The candidates converged on the same core shape (one `Intervention` type, a hook table over shared intercepts, a suppression context variable, diagnosis as a variant union, the replay ladder as data, a demo on real chromadb and the real openai SDK over `httpx.MockTransport`). That convergence is the strongest signal in the arena.

The base is opus because it is the only candidate sound on all three load-bearing mechanisms. Its diagnoser is pure over an injected replay callable. One intercept serves chromadb, pinecone, and the decorator, with modes that stop `contexteval run` from writing production traces. Its flaky demo case survives `run` and `diagnose` as separate processes. Fable and sonnet kept the flaky counter in memory, so the shell workflow would mislabel it. Haiku never suppressed the SDK's own LLM calls, so grader calls would become production traces.

**Grafts. These are binding on implementation.**

1. From fable. Diagnosis variants carry their evidence as data. `Irrelevant.removed` and `Ignored.gold_at` hold the chunk positions (retrieval index, chunk index) involved, so the UI says "removing chunks 3 to 8 fixed it" from data. `explain()` becomes a projection.
2. From fable. Tests for DoD item 4 (UI endpoints serve stored data) and for idempotence (a second `diagnose` is a no-op). Each test docstring names the defect it catches.
3. From sonnet. Error policy at the hook. Recording errors are swallowed and logged once. Intervention errors propagate as `InterventionNotApplicable`, for example a `top_k` override on a site with no top_k parameter. The retrieval is never called twice. Replaces the base's "fall back to call(args) unchanged", which would silently turn an experiment into a baseline run.
4. From sonnet. `@retriever(..., text=, rebuild=)` accepts callables for result items that are neither `str` nor `Mapping`. Replaces the base's `copy.copy(first_item)` injection.
5. From sonnet. The 80% token rule is checked inside a sliding window of about 1.5 times the evidence length, not across the whole text. Without the window a long prompt matches short evidence on scattered common words. This amends plan item 1.
6. From haiku. `_hooks.patch_method` reads the method from `owner.__dict__`, never `getattr`, so a subclass is not wrapped with its parent's method.
7. From haiku. `init(pinecone_text_key="text")` names where pinecone keeps chunk text.

**Fixes to the base.**

- Import cycles. `Trace.in_prompt` becomes a stored field computed by the capture layer when the trace is finalized, not a property that imports `_text`. `install` moves to `_hooks`, and `_capture` no longer imports `_hooks`.
- `JudgeVerdict.NO_FAILURE` is accepted. Unlabeled production traffic is mostly fine, and forcing a failure label would mislead. This amends plan item 4 for judge labels only.
- The flaky rerun runs first for every ground-truth case, including missing ones (plan item 3 read literally).
- The DoD item 3 assertion excludes the flaky planted case, because its alternating answers are noise in an experiment table.
- `_DecoratorCodec` with `top_k=None` and a `top_k` intervention raises `InterventionNotApplicable` (graft 3).

**Rejected.** Fable's opaque callable transforms (not storable or showable). Sonnet's flat `Trace` with optional fields. Haiku's deterministic trace ids, which overwrite history on a second run. Fable's `hooks/` subpackage (six one-line pass-through modules).

## Tradeoffs accepted

- We accept class-level monkeypatching, which can break on library updates, in exchange for zero app changes. Candidate target lists and an `incompatible` status make drift visible in `InstallReport`, not silent.
- We accept that an intervention applies to every retrieval call in a run, including injecting evidence into each one, in exchange for a single rule that needs no call-site identity (plan item 8).
- We accept that production trace boundaries come from a heuristic (one LLM call closes the buffer) in exchange for capture without a run wrapper. Multi-call agents get split into several traces.
- We accept that replay traces are not stored, only their outcomes inside the diagnosis, in exchange for a schema with one trace kind per run.
- We accept the `Trace.in_prompt` column as a write-only denormalization of a derived property, in exchange for a UI that reads one row.
- We accept that `run_experiment` always prepends a baseline row, which costs one extra pass, in exchange for every table having a comparison.
- We accept that chromadb multi-query calls are recorded but never intervened on, in exchange for codecs that handle one result row.
- We accept underscore module names, which look noisy in imports, in exchange for an enforced public boundary.

## Alternatives considered

- **Per-library hook classes with their own intercept logic.** Each hook would apply interventions and record events itself. That hides less, because the policy is repeated in four places, and a new transform would need edits in each. The codec-plus-shared-intercept shape keeps policy in one function and library knowledge in one table.
- **A `@contexteval.trace` or explicit `with contexteval.run():` wrapper instead of a context variable set by the runner.** That puts lifecycle on the caller. It is clearer for production, but it breaks the "no app changes" promise and gives two ways to start a run.
- **Labels as an enum plus optional fields (`label`, `cause`, `confirmed`, `verdict`).** That admits `label=ignored, cause=dropped`. The variant union deletes those states and the comment that would explain them.
- **Demo app LLM as a direct call into a fake (no openai SDK).** It is simpler, but the acceptance test would never cross the real hook path. The MockTransport costs a dev dependency and buys fidelity.

## Implementation reconciliation

P0 and P1 (branch `p1-capture`). Where the code departs from the sketch, and why.

- `install()` and `init()` live in `_hooks`, not `_capture`. The sketch kept `init` in `_capture` with a lazy import of `_hooks`. Moving both makes the import graph a line (`types <- _text <- _intervention <- _capture <- _hooks <- __init__`), and `init(pinecone_text_key=)` (graft 7) is library knowledge anyway. `_capture` keeps `InstallReport`, `Mode`, `set_mode(mode, make_sink)`, and a `reset_process()` test seam. The sink factory runs only when the mode actually escalates, so a user `init()` under `contexteval run` opens no database.
- `InterventionNotApplicable` is defined in `_intervention` and exported from the package root. It propagates through the user's own retrieval call, so app code may need to name it.
- `Trace.in_prompt` is a required constructor field. `_capture.finalize_trace(run, outcome, latency_ms, test)` is the one place that fills it (via `_text.in_prompt_pairs`) along with `Metrics`. The runner (P2) and the production sink both call it.
- `@retriever` takes `text=` as a key, attribute, or callable, and `rebuild=` for building injected items (graft 4). Items that are neither `str` nor `Mapping`, and empty results, raise `InterventionNotApplicable` on injection unless `rebuild` is given. The sketch's `copy.copy(result[0])` is gone.
- Chroma multi-query calls: `decode` reads row 0 and `encode` raises `InterventionNotApplicable`. The sketch said "recorded per row"; one event per call keeps `source_index` meaningful.
- Production traces take their question from the first retrieval's query text, or `""` when the call had none. The LLM adapter exposes only the flattened prompt.
- `Store` gained `close()`, `find_project()`, and `PROJECT_DIR_NAME`; the connection uses `check_same_thread=False` because the production sink flushes from whichever thread made the LLM call.
- `_cli.COMMANDS` maps names to `Command(run, help, add_arguments)` rather than bare callables, so the parser is generated from the same table that dispatches. `save_config` and `require_project` were added.
- `_llm.cost_usd` is implemented (finalize needs it). `PRICES` still holds only `fake`, so app-call cost is `None` until P6 fills the table.
- `demo/app.HashEmbedding` is implemented early because the hook tests need an offline embedding. chromadb 1.x requires `name()`, `get_config()`, `build_from_config()` and an explicit `__init__` on custom embedding functions.
- anthropic 1.x ships its own `httpx2`; the anthropic hook test uses `httpx2.MockTransport`. The openai test uses `httpx.MockTransport` as planned.
- The P3/P4 test sketches (`test_acceptance.py`, `test_diagnose_table.py`) carry a module-level skip marker naming the phase instead of failing on `NotImplementedError`.
- The pinecone codec synthesizes injected matches as `type(matches[0])(id=, score=, values=, metadata=)` and falls back to a small attribute-and-item object when that constructor refuses the kwargs.

P2 (branch `p2-runs`).

- The demo retrieves `TOP_K = 4`, not 3. The not_retrieved gold ranks 5th for its question, inside the 5-to-10 band, so `top_k=10` retrieves it. `tests/test_demo.py` asserts every planted rank directly, plus the replay outcomes each label needs (inject, gold to top, only gold) through `_runner.execute` with the real gold transforms. A corpus edit that would change a P3 label fails there first.
- `Planted.expected` is `Label | None`. `None` marks a healthy case that passes at baseline (`passes_baseline`). PLANTED holds six failure cases and two healthy ones. The irrelevant case's distractor is a chunk tagged `[FORUM]`. `planted.write_jsonl` and `python -m contexteval.demo.planted` write the import file.
- `fake_llm.evaluate(rule, question, chunks, state_file)` holds the rule match so tests can call it without HTTP. The transport resolves the default state file per request, so a cached client follows the cwd's project.
- The demo collection is persistent, not ephemeral. It lives at `app.data_dir()/demo_chroma`, beside the flaky state file. `data_dir()` is `<project>/.contexteval`, or a temp directory when no project is found, so the demo never creates a project the user did not ask for. The collection is upserted once per process per path, which is idempotent. Reason: chromadb 1.5.9's ephemeral client drops an older collection's vector index once enough other collections are opened in the same process. `count()` still reports every row, but queries return nothing. In the full suite this happened about one run in three (`test_hooks` opens many collections). A standalone probe reproduced it after 23 and 53 extra collections. A persistent index never lost results in 3 runs of 120 extra collections each. Hook tests still use ephemeral clients.
- Providers take an optional `client` (an SDK client) so tests inject a mock transport. The default OpenAI model is `gpt-4.1-mini`. `AnthropicProvider` keeps `claude-haiku-4-5` as its default because current Claude models (Haiku 5.5, Sonnet 5.5) return a 400 on non-default sampling parameters. For those models temperature is omitted. For older models it is sent as `extra_body={"temperature": 0}`, because anthropic 1.x removed `temperature` from `messages.create`'s signature. `PRICES` covers gpt-4.1-mini, gpt-4.1-nano, gpt-4o-mini, claude-haiku-4-5, claude-haiku-5-5, claude-sonnet-4-6, and claude-sonnet-5-5.
- `_runner.execute` re-raises `InterventionNotApplicable` instead of storing it as a crash, per graft 3. Every other exception still becomes `Crashed`.
- The sketch's `run_suite` name is kept. `_runner.estimate_grading` is new. It is the `run` command's estimate, and it assumes that every case needs one LLM grade (worst case). The app's own calls are reported from the last baseline run when one exists, because the app model is unknown before the run.
- `build-tests --import` makes no LLM calls, so it prints no estimate and asks for no confirmation. The import's test set is the file stem. Generated cases go to the `synthetic` test set. `import_tests` also reads `.csv` files.
- `confirm` treats EOF or an unreadable stdin as "no" and exits 2, so a script that omits `--yes` never blocks.
- `run_experiment` is still `NotImplementedError` (P4).

P3 (branch `p3-diagnose`).

- `locate_gold` returns a `GoldMap(location, gold, other)`, not a bare `GoldLocation`. `gold` and `other` are the in-prompt delivered chunk refs with and without the evidence. They are the data graft 1 asks `Ignored.gold_at` and `Irrelevant.removed` to carry, and computing them in the same pass that decides the location keeps one function reading the trace. `diagnose_case(gold: GoldMap, replay)` takes the record. The table test builds it directly.
- `LADDER` rows are `(ReplayStep, Builder)` where `Builder = Callable[[Replays, GoldMap], Diagnosis]`, instead of `(ReplayStep, type[Ignored] | type[Irrelevant])`. The two variants take different evidence fields, so a bare class could not be called uniformly. The row order is unchanged and `test_ladder_prefers_the_least_invasive_fix` pins it.
- `make_replay` takes the run's own `Intervention` as `base` and applies the replay transform after it. `diagnose_run` passes `run.setting.intervention()`, so diagnosing an experiment run reruns under that setting rather than silently under baseline. For a baseline run this is the no-op intervention.
- Replay cost is 2 to 3 app calls (`MAX_REPLAYS = 1 + len(LADDER)`), not the sketch's "2 to 4". The CLI reports `up to N replay calls` from that constant.
- The judge reply is parsed by `parse_verdict`, which accepts the JSON object inside a code fence or surrounding prose and raises `JudgeReplyError` for anything without a known verdict. `cmd_diagnose` turns that and `ProviderError` into a `UserError` that says the diagnoses so far are saved, because `diagnose_run` commits per trace and the next run resumes.
- `pending(store, run, force)` is the one list of traces to diagnose. The estimate and the loop both read it, so the cost prompt and the work agree. The estimate counts one judge call per judge-path trace and, worst case, one grade per replay for ground-truth cases; app calls are reported on a separate line, as `run` does.
- `diagnose_run` takes an `on_diagnosis` callback so the CLI prints each label as it is saved. `DiagnoseReport` keeps the three counts from the sketch.
- `diagnose_run` with `app=None` on a run that holds a ground-truth case raises `ValueError` instead of falling back to the judge, so a CLI wiring mistake cannot relabel a baseline run with judge verdicts.
- `FakeProvider` already answered `Task.JUDGE` with `no_failure`; nothing was added there. Tests that need another verdict pass a handler.
- The P4 acceptance test keeps its own skip marker; the module-level skip is gone.

P4 (branch `p4-experiment`).

- `parse_grid` derives each knob's parser from `typing.get_type_hints(Setting)`. An Enum field parses by value, a `Literal` field by membership, and an `int | None` field with `int`. A field of any other type raises `TypeError` at parse time, so a new kind of knob fails loudly instead of being skipped. A knob given twice is an error, not a merge.
- `_runner.experiment_settings(grid)` is new. It returns BASELINE first and then the grid with duplicates and BASELINE removed. `run_experiment` runs that list and the CLI cost estimate counts it, so the two cannot disagree. Each setting is one `run_suite` call with the experiment id, so experiments use the same path as `contexteval run`.
- The experiment command takes the app as an optional leading positional (`contexteval experiment [module:function] knob=v1,v2 ...`), the same as `run`. The sketch's `--app` flag is gone. A first token with `:` and no `=` is the app. Without one, the app comes from `config.app`, which `run` remembers. Experiments run every stored case. There is no `--test-set` flag yet.
- Setting names keep the space-separated form from P1 (`top_k=10 order=ends`), not a comma-separated one. A comma already separates alternative values in the grid syntax, so `top_k=10,order=ends` would read as one knob with two values.
- `InterventionNotApplicable` during an experiment becomes a one-line `UserError`. The runs finished before it stay stored under the experiment.
- The DoD item 3 test lives in `tests/test_experiment.py`, not `tests/test_acceptance.py`, so the P3 and P4 owners never edit one file at once. The skipped DoD item 3 placeholder in `test_acceptance.py` is left for that file's owner to delete.
- The transform tests asked for in P4 (lexical rerank, ends order, compress, max_chunks) already existed in `tests/test_intervention.py` from P1. No new ones were added.

P6 (branch `p6-real`).

- The demo app's model is `gpt-4.1-mini`, the same as the SDK provider default, so the real-API run prices every call from one table row.
- The planned lint against importing `contexteval._*` from outside the package is dropped. Nothing outside the package imports it except the tests, which use internals on purpose, so the lint would check no code.
- `build-tests` already had `--per-passage`, and the demo corpus is four one-passage documents, so no case cap was added.
- The CLI prints estimates only. Neither the SDK's own calls nor replay calls record their actual spend, so the real-API run measured cost with a scratch wrapper around `Completions.create`. The README tells users to read their provider's usage page.
- `pyproject.toml` uses an SPDX `license = "MIT"` with `license-files`, which needs setuptools 77 or later.

Review fixes, capture (X). Branch `fix-capture`, from the four-model review of v1 (commit 60f248b). Items X1 to X10; each has a test whose docstring names the defect.

- X1. `init()` never raises. It catches everything, logs once, and returns `InstallReport(statuses={}, error=...)` with nothing hooked, so the app runs as if `init()` had not been called. `InstallReport` gained `error: str | None` and the status `failed`: `_install_spec` and `patch_method` report it for an exception (a library import with a failing side effect, a target `inspect.signature` cannot read) and leave that library unhooked while the others install. Under `contexteval run`, `init()` no longer opens the database, since the mode cannot escalate.
- X2. The production buffer is `_Ambient`, not a reused `ActiveRun`: a deque of at most `AMBIENT_MAX_EVENTS` (32) stamped retrievals per context. `intercept_llm` takes it out of the context before the call, so a call that raises drops it. Pairing happens in `_Ambient.close`: events older than `AMBIENT_MAX_AGE_S` (60 s) are stale; when any recent event shows in the prompt (its query or a delivered chunk), the recent events that do not belong to an earlier request; when none shows, every recent event stays so a filtered-out context is still visible. The question is the first kept event's query. Both intercepts keep one path: `ActiveRun` and `_Ambient` share `intervention`, `question`, and `record`.

v2, auto-sweep (branch `v2-sweep`). `contexteval sweep`, the second v2 roadmap item: the labels of the latest diagnosed baseline run choose the experiments, and the command ends with one plain recommendation. Each test's docstring names the defect.

- Module: `_sweep`, beside `_diagnose`, so the package has fourteen modules. It imports `_runner.run_suite` and `_store`, and `_cli` and `_ui` import it. Nothing new runs an app: every sweep run is `run_suite` under one experiment, the path `contexteval run` and `experiment` use, so there is one runner and a sweep is an experiment row set like any other.
- Data first. `FailureKind` is the label split by the cause that decides the fix (`missing/not_retrieved`, `missing/dropped`, `irrelevant`, `ignored`, `not_context`, `flaky`), and `kind_of(diagnosis)` is an exhaustive match; a judge `missing` has no cause and takes the retrieval candidates, a judge `no_failure` takes none. `POLICY: Mapping[FailureKind, Fixable | Unfixable]` is the design-notes table ("mostly missing, try higher top-k; mostly irrelevant, try reranker, lower top-k; mostly ignored, try reordering, compression") as data, with the reason text for the kinds no setting can change (a dropped chunk was removed by the user's own code; not_context and flaky are not context problems). A candidate is a `Setting` or a `Scaled(knob, factor)`, an integer knob relative to k, the most chunks one retrieval returned in the source run, so `top_k` candidates are 2k and 3k (the audit's bot at k=4 was fixed by 8) and `max_chunks` is k/2; a resolved value that would change nothing (max_chunks at or above k) is dropped. `rank_candidates(counts, k)` weights each setting by the failures whose label proposes it, so a setting two labels share carries both counts, and `--max-settings` cuts the lightest. `Split(seed, fraction, tune, holdout)`, `Plan`, and `SweepReport` are frozen records; `SweepReport.to_json` is the experiment's `report` column and `recommendation_line(report, rows)` is a projection both the CLI and the dashboard print, so the line is never stored.
- Search shape. Two were sketched. (a) One round: run the ranked single-knob candidates on the tune cases, pick the best, confirm it on holdout. Cost 1 + C tune runs plus 2 holdout runs; it can never find that two labels need two knobs at once. (b) Greedy rounds: round 1 as (a); each later round merges the best setting so far with every round-1 candidate that changes other knobs and did not lose to the baseline, and stops when the best is the baseline or every combination has run. (b) won because real runs carry mixed labels (the demo's one missing and one ignored case need `top_k` and a reorder or rerank together, and (b) finds `top_k=8 rerank=lexical` at 5 of 8 where (a) stops at 4 of 8), while its extra cost is bounded and visible: the estimate counts every round full, and a run whose labels are all one kind (the real bot, five `missing`) has no partner for round 2 and stops after round 1 at the same cost as (a). A full grid over the candidates was rejected as C squared runs for the same combinations, and a per-label winner merge (one winner per kind, merged blind) because it would combine a setting that lost to the baseline.
- Overfitting guard. `split_cases` is seeded (`random.Random(seed)`) and stratified by the source run's pass or fail, so both sides hold failures the candidates can fix and a holdout check is never vacuous; the default holds out 0.3. The choice is made on the tune rows and the winner is confirmed against a fresh baseline on the holdout cases. Recommend only when the winner passed more tune cases than the baseline and at least as many holdout cases; otherwise the line says to keep the current settings and why (no candidate beat the baseline, or the winner lost on holdout). `--holdout 0`, or a set so small every stratum rounds to zero, tunes on every case and the line says the result is unconfirmed. `test_a_setting_that_wins_on_tune_but_loses_on_holdout_is_not_recommended` builds the loss with a scripted app that passes exactly the tune cases under `top_k=4`; with the guard replaced by `if True:` it fails on the final line, which then reads `Set top_k=4`.
- Ranking reads the experiment table rows, so the numbers the user sees decide. It was `(-accuracy, mean input tokens, mean latency)`; the tie-break entry below replaces it with a tolerance window. `beats` is a strict pass-count comparison on the same case set. The final line is `Set <setting>. Accuracy a% -> b% (holdout c% -> d%). Uses n% more|fewer input tokens; mean latency x ms -> y ms.` Known artifact: the baseline is the first run of the process, so on the demo its latency carries chromadb's index warm-up (21 ms against 3 ms); the `experiment` table has the same shape and the README says so.
- Store. `experiments` gains `kind` (`manual` or `sweep`) and `report` (the sweep's JSON), `ExperimentRow` gains `run_id` so a report can name rows, and `Store.experiments()` returns `ExperimentInfo` records. - Real-bot check (`examples/realbot`, fresh project, `init --provider openai --model gpt-4.1-mini`, `build-tests --per-passage 1` giving 23 synthetic cases plus the 28 customer questions, `run`, `diagnose`, `sweep` with defaults). The run passed 46 of 51; the labels were 4 `missing/not_retrieved` and 1 `ignored`, so the candidates were `top_k=8` (4), `top_k=12` (4), `order=ends`, `order=reverse`, and `compress=2` (1 each), and `rerank=lexical`, which the audit found made this bot worse, was never proposed because no failure was `irrelevant`. On the 35 tune cases the baseline passed 32, `top_k=8` 34, `top_k=12` 35, and the three reorder and compress settings 31, 31, and 28, so round 2 had no partner that had not lost and the search stopped. On the 16 holdout cases the baseline passed 14 and `top_k=12` 15. The line read "Set top_k=12. Accuracy 91% -> 100% (holdout 88% -> 94%). Uses 174% more input tokens; mean latency 860 ms -> 855 ms." The audit reached `top_k=8` (99% of 75 cases, 88% more tokens) by hand; the sweep went one step further because `top_k=12` passed one more tune case (the Metro-E payload question, whose chunk the audit found never ranks in the top 8) and accuracy ranks before tokens. Caveats on the numbers: the bot samples at its default temperature and each setting ran once, so a one-case difference on 35 or 16 cases is inside that noise; the direction (a larger `top_k`, never a rerank) is the finding, not the exact k. The whole check made 770 OpenAI calls and cost $0.0962 by the audit's tally script (`audit/ce.py`, `audit/spend.py`), of which the sweep was 573 calls and $0.0733.

v2, sweep tie-break (branch `v2-tiebreak`). The owner chose to prefer the cheaper setting among near-ties. `choose(rows, baseline_passed, tolerance)` is the one ranking function. With `top` the most tune passes among the rows, every row that passed at least `top - tolerance` cases and more than the baseline contends, and the fewest mean input tokens wins, then the lowest latency, then the most passes. When no row beats the baseline, only the rows at `top` contend, which keeps the accuracy-first pick for the "no candidate beat the baseline" reason. Each round's best setting, the final winner, and that reason all call `choose`, so rounds and the final pick agree. The recommendation rules stay: more tune passes than the baseline and at least as many holdout passes. `SweepReport.passed_over` names the most accurate tune run when a cheaper one was recommended (an older report without it reads as none), and the line states its cost, as in "Set top_k=8 (top_k=12 passed 1 more tune case but uses 50% more input tokens)". The window scales with the set, because the noise in a pass count does. The first cut was a fixed `--tolerance` of 1 case; on the 8-case demo one case is 12.5 points, and that default recommended `rerank=lexical max_chunks=2` (4 of 8, 74 tokens) over `top_k=8 rerank=lexical` (5 of 8, 217 tokens), the setting that fixes the planted not_retrieved case. Now `Plan.tolerance` is `None` by default and `Plan.window` resolves it to `NEAR_TIE_PERCENT` (5) of the tune cases in integer arithmetic, rounded down: 0 cases on the demo's 8, 1 on 35, 5 on 100. `--tolerance N`, a whole number checked at the CLI, overrides it, and 0 restores accuracy first. The window is resolved in the plan, once the split is known, so `choose` still takes a case count. `_print_plan` prints `Plan.window_note` when the window is not 0, as in "near-tie window: 1 case (5% of 35)" or "near-tie window: 2 cases (--tolerance)". By the recorded tune numbers, the real-bot check above (35 tune cases, `top_k=8` 34 at fewer tokens, `top_k=12` 35) would now take `top_k=8`, the setting the audit reached by hand; that is inferred, not rerun. `test_demo_sweep_recommends_a_larger_top_k_and_names_the_dropped_case_as_unfixable` and `test_default_window_on_10_cases_is_accuracy_first` fail with the window fixed at 1. With the floor reduced to `top - tolerance`, `test_a_near_tie_that_does_not_beat_the_baseline_is_never_chosen`, the demo test, and the nothing-to-do test fail.

v2 review fixes, capture (P) (branch `v2-fix-capture`). From the four-model review of v2 (`docs/review-v2-2026-10-11.md`), items P1 to P7. Each fix has a test whose docstring names the defect, committed red before the fix.

- P1 and P2, one design change. `capture.InstanceTopK` is deleted. `RetrievalCodec.override_top_k(args, top_k) -> Restore | None` is the one method: the argument form (`args.arguments[top_k_param] = top_k`, no restore) is implemented once on the protocol, and the codecs subclass it explicitly to inherit it (`ChromaCodec`, `PineconeCodec`, `_DecoratorCodec`, the test's `_BrokenCodec`). The framework codecs override it, set the retriever's own knob, and return the restore. The LangChain codec sees the bound call and first overrides a per-call `k` in the `**kwargs`, because `VectorStoreRetriever._get_relevant_documents` computes `self.search_kwargs | kwargs`, so `invoke(q, k=1)` under `top_k=4` used to retrieve 1 document while the event said `k: 4`. A codec raises `InterventionNotApplicable` when its site cannot apply the value; that no longer ends the call.
- Ownership handoff, sketched before coding. `_retrieving` holds `_Outermost(top_k, applied, refusal)` instead of a bool. (1) The outermost hooked retrieval in a context creates it with the run's `top_k` and offers the value to its own codec (`_take_top_k`); applied, `applied = (knob name, value)`; not, `refusal` keeps that codec's reason and the value stays pending. (2) Every hooked call underneath, in the same context, sees the state. When the value is pending it offers it to its codec; when that applies, the inner call gets an `_InnerOverride` that restores its knob when its own call returns, and records nothing; when it cannot, or the value was applied already, it passes through as before. (3) The outer `finish` refuses through `_refuse` with the outer codec's own reason when the value is still pending, so `run.not_applicable` and the messages the tests match (`langchain: top_k=5 ... no search_kwargs or k`, `no top_k parameter`) are unchanged; otherwise it writes `params[knob] = value` and goes on to decode, transform, and record as the only event. The event names the knob that was set: `k: 4` on a `VectorStoreRetriever`, `n_results: 4` on a custom `BaseRetriever` over chromadb, `similarity_top_k` on LlamaIndex. What moved: the refusal comes after the call instead of before it, so a retriever with no knob anywhere runs once at the user's `k` before the experiment stops (it never ran before). The thread-pool limit stands: a worker thread has no copy of the state, so a store queried there records its own event and takes `top_k` itself. Rejected: a LangChain codec that knows wrapper fields (`base_retriever`, `retrievers`), because the wrapped retriever's own hooked `invoke` already fires underneath and the handoff covers every wrapper shape at once; and keeping the pre-call refusal, which would need to know before the call whether a hooked call will happen underneath. Tests: `test_custom_langchain_retriever_over_hooked_chroma_takes_top_k_from_the_inner_call`, `test_wrapper_retriever_hands_top_k_to_its_base_retriever`, `test_per_call_k_is_overridden_and_the_event_records_the_applied_value`, `test_decorated_function_without_a_knob_takes_top_k_from_the_hooked_store_inside`. Before the fix the first two and the fourth refused and the third returned 1 document.
- P3. A migration step is `_AddColumn(table, column, definition)` and checks `PRAGMA table_info` before it alters. `_migrate(conn, version)` runs one version's steps and the `PRAGMA user_version` bump inside one `BEGIN IMMEDIATE` transaction and re-reads the version under the write lock, so a second process that finds the step done applies nothing. `executescript` is gone from the migration path (it commits before it runs and after each statement). `test_migration_rerun_after_a_partial_step_opens_cleanly` opens a database left after the first `ALTER` and one left after both with the version unbumped; both failed before with "duplicate column name: kind". `test_migration_steps_and_version_bump_commit_together` injects a failing second step and checks the first column was rolled back; a mutant that commits between steps fails it.
- P4. `override_attr` moved from `_hooks` to `_capture`, beside `Restore` and `reset_process`. It calls `setattr` before recording the entry, so a setter that rejects the value leaves nothing behind; before, the leaked depth-1 entry made the next override's restore only decrement and the retriever kept the experiment's value (`test_failed_knob_setattr_leaves_no_entry_and_a_later_restore_restores`, through a LlamaIndex retriever whose `similarity_top_k` setter caps at 10). `forget_knobs()` runs from `reset_process()` and `uninstall_all()`.
- P5. `_snapshot(codec, args)` logs once and returns `{}` when an argument cannot be read, the same policy as the other recording errors. Before, it ran after the override with no guard, so the exception left the hook before the call and the knob stayed overridden (`test_snapshot_failure_leaves_no_override_behind`, a `Mapping` config whose `items()` raises; the retriever was left at `k=4`).
- P6. `HookSpec.only_if_imported` marks the four framework rows. `install(mode="production")` reports `not_imported` for such a library that is not in `sys.modules` at `init()` time and never imports it; the CLI path imports and hooks everything it can. `InstallReport` and `Status` gain `not_imported`, ranked between `installed` and `not_installed`. Measured here: `import langchain_core.retrievers` 0.65 s and `import llama_index.core.base.base_retriever` 1.21 s after `import contexteval` (0.1 s); the reviewer saw 7.7 s and 2.8 s. `test_production_init_hooks_a_framework_only_when_the_app_imported_it` runs three fresh interpreters: cold production `init()` (both `not_imported`, neither in `sys.modules`), production after `import langchain_core.retrievers` (`installed`, `not_imported`), and `install("cli")` (both `installed`). The README says to call `init()` after importing the framework.

## Open questions and risks

- Should the flaky rerun also run before the missing confirmation? The sketch runs it first for every ground-truth case, reading plan item 3's "before replay" literally. The other reading skips it for missing, which saves one call per missing case.
- Is `JudgeVerdict.NO_FAILURE` acceptable? Plan item 4 lists no "ok" label, but unlabeled production traffic is mostly fine, and forcing a failure label would mislead.
- Pinecone chunk text key defaults to `metadata["text"]`. Should `init()` take a `pinecone_text_key`, or should a config file own it?
- Risk: the hashed-embedding demo needs a hand-tuned corpus so the planted gold ranks exactly 5th, 2nd, and 1st. The acceptance test should assert ranks directly so a corpus edit fails loudly.
- Risk: `FlipFlop` makes the flaky case alternate across experiment runs, so its row is noise in the experiment table. Should the experiment test exclude it?
- Risk: production mode writes to SQLite on the user's hot path. WAL mode and swallow-and-log on write failure are the plan. Is sync write latency acceptable for v1? Resolved by review fix X3: the hot path enqueues and a writer thread stores.
- `_DecoratorCodec` injection for object items uses `copy.copy(first_item)` with the text field set. Is that acceptable, or should object-returning retrievers be required to pass an explicit builder?
